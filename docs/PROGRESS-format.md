# PROGRESS.md 格式規範（lq-progress v1）

萊乾資訊後台（`/admin/cases/[id]`）會讀取每個案件 repo 的開發進度並算出百分比。
把下面這份格式放進 repo 根目錄的 `PROGRESS.md`，後台就會優先採用它。

## 範本

```markdown
# 專案進度
<!-- lq-progress: v1 -->
> stage: 開發中
> updated: 2026-08-09

## 階段一：基礎建設
- [x] 建 repo 與 CI
- [ ] 接 Supabase
  - [ ] 這是子項，不計入分母

## 階段二：功能開發
- [ ] 打卡 API
- [ ] 報表匯出
```

上面這段是**程式碼區塊**，所以解析器不會把它當成真的進度項目——這也是本檔案自己的
「圍欄跳過」驗證素材（見下方〈驗證〉）。

## 解析規則

| 規則 | 說明 |
|---|---|
| 項目行 | `- [ ]` / `- [x]`（`*`、`+` 也可）。`[X]` 大寫視同完成 |
| 非項目 | 括號內是其他字元（`[~]`、`[-]`、`[o]`）→ 整行忽略，**不計入分母** |
| 分母 | 只算「該檔最小縮排層級」的項目。巢狀子項會顯示但不計數，避免細項稀釋百分比 |
| 程式碼區塊 | ` ``` ` 與 `~~~` 圍起來的內容全部跳過（擋掉文件裡的範例勾選框） |
| 分組 | 最近一個前置的 `## ` 標題。第一個 `##` 之前的項目不分組、也不畫分組小條 |
| metadata | H1 之後連續的 `> key: value`，只認 `stage`、`updated`、`note` |
| 版本註記 | `<!-- lq-progress: v1 -->` 選填，只在多個候選檔案時加權 |

**上限**：檔案 > 200KB 不解析；項目最多 300 筆、分組最多 20 組、commit 最多 10 筆。

## 後台的取用順序

1. **`PROGRESS.md`**（repo 根目錄）—— 有就用它，恆勝。
2. **`docs/plans/` 裡挑一個**（沒有 1 時）。檔名評分：`progress` +100、`checklist` +40、
   `implementation` +20、`plan` +10、`design` −50、`gap`/`spec` −50；同分則檔名尾端數字大者優先
   （`P4-progress.md` > `P1-progress.md`）。取前 3 名依序解析，**第一個解析出項目的勝出**。
3. 都沒有 → 只顯示 **commit 活動**（最近 10 筆訊息、最後 commit 時間、幾天沒動）。

第 2 條的「解析後才採用」不可省：實測 `apollo-100-parity-checklist.md` 檔名分數很高，但全檔是表格、
0 個勾選框；`nina` 的 8 個 plan 檔也全部沒有勾選框。想強制指定就放根目錄 `PROGRESS.md`。

## 百分比之外要看的東西

進度檔會過時。後台在百分比旁一定會並列 **最後 commit 距今幾天**，並標示這個數字**來自哪個檔案**。
「100% 但 30 天沒動」跟「60% 但今天還在 commit」是完全不同的狀況，只看百分比會誤判。

## 驗證

這份文件與 repo 根目錄的 `PROGRESS.md` 是解析器的永久 fixture：

- `?path=docs/PROGRESS-format.md` → 應解析出 **0 個項目**（範本全在程式碼區塊內）
- `?path=PROGRESS.md` → 頂層項目計入分母、`  - [ ]` 子項不計入

指令見 `README.md` 的「GitHub 進度」段落。
